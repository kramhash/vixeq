# 1.0 Release Checklist

This checklist is the release-readiness gate for `1.0.0-rc.1` and `1.0.0`.
It does not publish by itself; it records the required checks and release order.

## Preconditions

- P0-P8, T0-T8, R0-R6, RC1A-RC1K, and RC2 are `done` in
  [`../plans/v1-collaboration-spec.md`](../plans/v1-collaboration-spec.md).
  `1.0.0` additionally requires RC3.
- `CHANGELOG.md`, package READMEs, generated API docs, migration guides, and
  [`../../SUPPORT.md`](../../SUPPORT.md) describe the public behavior being
  released.
- Public package versions are bumped in lockstep.
- API Extractor reports are current for all public packages.
- The working tree contains no unrelated release artifacts such as `.tgz`,
  `.tmp/`, copied example output, or generated probe files.
- The Core branch-coverage gap recorded in the 0.9 release checklist is closed
  (`pnpm test:coverage` meets the configured thresholds and is wired into
  `.github/workflows/ci.yml`), or a new approved decision re-scopes the gap.
  `1.0.0-rc.1` must not publish while this gap is open and undecided.

## Required Local Gates

Run these from the repository root before publishing an RC or stable release:

```sh
pnpm typecheck
pnpm build
pnpm test
pnpm test:coverage
pnpm api:check
pnpm behavior:check
pnpm smoke:pack
SMOKE_REACT_VERSION=18 pnpm smoke:pack
SMOKE_TS_VERSION=5.5 pnpm smoke:pack
SMOKE_TS_VERSION=7.0 pnpm smoke:pack
pnpm test:e2e
```

`pnpm test:coverage` also runs in CI on the Node 22 build leg; the Node 24 and
26 legs run the ordinary workspace test suite.

## Publish Workflow

Releases publish only through `.github/workflows/publish.yml`; do not run
`pnpm publish` by hand.

- A `v<version>` tag push runs, in order:
  1. `preflight`: `scripts/release-meta.mjs` checks that the root and the
     three public package versions are in lockstep, that the tag is exactly
     `v<version>`, and that `CHANGELOG.md` has a non-empty `## <version>`
     section; then that the tagged commit is on `main`.
  2. `gates`: the whole CI workflow (`ci.yml`, called as a reusable
     workflow): the Node 22/24/26 build matrix with every local gate above,
     browser E2E, and the docs site build.
  3. `publish`: builds, publishes `@vixeq/core`, `@vixeq/react`, and
     `@vixeq/player-react` with provenance under the `next` dist-tag for a
     prerelease version (`1.0.0-rc.1`) or `latest` for a stable version,
     checks that each dist-tag now points at the version, creates the
     GitHub Release `v<version>` (marked pre-release for a prerelease) whose
     notes are the CHANGELOG section, and then fails the run if any of the
     three versions has no npm provenance attestation (`dist.attestations`).
     Provenance is requested with `NPM_CONFIG_PROVENANCE=true`: the filtered
     `pnpm publish` does not pass a `--provenance` flag on to npm.
- A manual dispatch (`gh workflow run publish.yml --ref main`) is a dry run:
  the same `preflight` (except the tag checks) and `gates`, then
  `pnpm publish --dry-run`. It exchanges no token, publishes nothing, and
  creates no Release. A version that is already on the registry is skipped
  by the dry run, so run it after the version bump. Also dispatch once right
  after RC2 merges, while RC1J and RC1K are still open: at the published
  `0.9.0` version the publish dry run skips every package, but `preflight`
  and `gates` still run, so workflow problems surface before the RC bump.
- Re-running a failed run is safe: a version already on the registry is
  skipped, and an existing GitHub Release is left unchanged.
- If `preflight` or `gates` fails, nothing was published: fix the problem on
  `main`, delete the tag (`git push --delete origin v<version>` and
  `git tag -d v<version>`), and tag the fixed commit. To abandon a run that is
  still in progress, cancel it first (`gh run cancel <run-id>`) and wait until
  it has stopped; a run left going would publish the old commit.
- If "Verify published versions and dist-tags" fails after the publish step
  printed `+ @vixeq/...` for every package, the registry was still processing
  them (the step waits up to 15 minutes). Wait until
  `npm view <pkg>@<version> version` succeeds for all three, then
  `gh run rerun <run-id> --failed`: publishing skips the existing versions,
  and verification and the GitHub Release run again.
- If only "Verify provenance attestations" fails, the versions are published
  without provenance and cannot be republished. Fix the workflow and publish
  the next version; do not re-tag.
- If the failure is in `publish` after some packages went out, re-run the
  failed job. Do not re-tag a version that is partly published; publish a
  new version instead.

## RC Publish Steps

1. Confirm the dist-tag state:
   `npm view @vixeq/core dist-tags --json` (`latest` is the previous stable).
2. Bump the root and the three public package versions in lockstep to
   `1.0.0-rc.1`, and rename `## Unreleased` in `CHANGELOG.md` to
   `## 1.0.0-rc.1 - <YYYY-MM-DD>`. That section becomes the GitHub Release
   notes; add the package links and known caveats there.
3. Re-run the required local gates after the version bump.
4. Commit, push `main`, and wait for CI to pass.
5. Rehearse: `gh workflow run publish.yml --ref main`, and wait for the dry
   run to pass (`gh run watch`). Required before the first RC published by
   this workflow.
6. Tag and push: `git tag v1.0.0-rc.1 && git push origin v1.0.0-rc.1`. Watch
   the Publish run to completion.
7. Verify npm metadata for all packages:
   `npm view @vixeq/core@1.0.0-rc.1 version dist-tags exports dist.attestations`.
   `next` is `1.0.0-rc.1`, `latest` is unchanged, and `dist.attestations` is
   present. The GitHub Release is marked pre-release. In the clean consumer
   of step 8, `npm audit signatures` reports verified attestations.
8. Install the published RC packages in a clean temporary consumer and repeat
   the packed-package smoke coverage against the registry packages.
9. Record gate results and the registry smoke result in the release notes
   (`gh release edit v1.0.0-rc.1`) and in `CHANGELOG.md`.

## RC Validation

Validate the RC in a real consumer before stable promotion (spec §2). This
replaced the 14-day observation window on 2026-10-30.

1. Upgrade the frapx integration lab from 0.9 to the RC, following only
   `CHANGELOG.md` and [`../migrations/`](../migrations/). Install from the
   registry with `--config.minimum-release-age-exclude='@vixeq/*'` if the
   local pnpm config sets `minimumReleaseAge`.
2. Type-check and build the lab.
3. Exercise every page in a browser: play, pause, seek, and audio sync.

Outcomes:

- A step the migration notes do not cover: fix the notes. The public API is
  unchanged, so promotion is not blocked.
- A blocker or critical defect, or one that needs a public API change: fix it,
  publish a new RC, re-run the required gates, and validate that RC the same
  way.
- Keep `latest` on the previous stable until stable promotion.

## Stable Promotion Steps

1. Confirm the final RC passed RC Validation with no open blocker or critical
   defects.
2. In one commit, before tagging: remove the pre-1.0 and release-candidate
   disclaimers (root and package READMEs, `SUPPORT.md`), bump the root and
   the three public package versions in lockstep to `1.0.0`, and add a
   `## 1.0.0 - <YYYY-MM-DD>` section to `CHANGELOG.md` with the known
   caveats. Package READMEs ship inside the tarballs and npm shows the
   `latest` tarball's README, so a disclaimer removed after publishing stays
   on the `1.0.0` package page. The same commit also updates the pre-1.0
   wording in `ROADMAP.md`, `AGENTS.md`, and `CLAUDE.md` (the S1 row of the
   task table lists every file).
3. Re-run the required local gates, merge through a PR (work after
   `1.0.0-rc.1` goes through PRs), and wait for CI on `main`.
4. Rehearse: `gh workflow run publish.yml --ref main`, and wait for the dry
   run to pass. Run it after the bump, since a version already on the
   registry is skipped.
5. Tag the merge commit and push `v1.0.0`; the Publish workflow publishes
   under `latest` and creates the GitHub Release.
6. Install the published `1.0.0` packages in a clean temporary consumer and
   repeat the registry smoke coverage.
7. Verify npm metadata and dist-tags for all packages (`latest` is `1.0.0`),
   then retire the prerelease tags by hand for each package:
   `npm dist-tag add <pkg>@1.0.0 next` and `npm dist-tag rm <pkg> beta`.
   The repository holds no npm write token (publishing uses the workflow's
   OIDC exchange), so run these logged in as a package owner (`npm login`)
   and pass `--otp=<code>` or answer the 2FA prompt. Confirm with
   `npm dist-tag ls <pkg>`: `latest` and `next` are `1.0.0`, and `beta` is
   gone.
8. Record package URLs, published dist-tags, gate results, and any known
   support caveats in `CHANGELOG.md` and the GitHub Release.
9. In a follow-up PR, move `examples/sandbox` (which installs the packages
   from the registry) to `^1.0.0` and update the lockfile; the range cannot
   resolve before `1.0.0` is published.

## Minor Releases After 1.0

Minor releases add API only, so they publish as stable without an RC:

1. Merge the version-bump PR (lockstep versions and a
   `## <version> - <YYYY-MM-DD>` section in `CHANGELOG.md`).
2. Run `pnpm build`, pack the three public packages
   (`pnpm --filter <pkg> pack --pack-destination <dir>`), install the
   tarballs in the frapx integration lab, and run RC Validation steps 2–3.
3. Dispatch the dry run (`gh workflow run publish.yml --ref main`), then tag
   the merge commit `v<version>` and push it.
4. Run the registry smoke on the published packages and record the results
   as in steps 6–8 above.

## Support Caveats to Record

- Browser support follows the locked Playwright browser set recorded in
  [`../../SUPPORT.md`](../../SUPPORT.md).
- WebKit and CI Firefox browser E2E do not assert real WebAudio playback
  start/progression when Linux headless Playwright cannot start or advance
  `AudioContext.currentTime`.
- Node 20 is not supported for the 1.0 line.
